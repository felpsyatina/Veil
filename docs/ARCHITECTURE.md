# Архитектура

## Зачем своя агрегация подписки, если у 3x-ui есть свой subscription-сервис

У панели 3x-ui (форк MHSanaei) есть встроенный механизм subscription — но он
отдаёт конфиги клиентов только **одной** ноды, на которой он включён. Каждая
нода в этом проекте — отдельный, ничего не знающий друг о друге инстанс
3x-ui. Чтобы в одной подписке пользователь получал сразу несколько разных
серверов (это было явным требованием), агрегацию нужно делать на своей
стороне: сохранять у себя, на каких нодах у подписки создан клиент, и
собирать единый список `vless://`-ссылок по запросу.

Это и есть эндпоинт `GET /sub/{token}` (`app/api/routes/subscription.py`),
который читает `SubscriptionServer` (см. ниже) и склеивает по одной ссылке
на каждую активную и здоровую ноду.

## Сервисы (docker-compose)

| Сервис | Что делает |
|---|---|
| `bot` | Telegram-бот (aiogram 3, long polling) — весь пользовательский и админский интерфейс |
| `api` | FastAPI — вебхуки платёжного провайдера + `/sub/{token}` |
| `worker` | APScheduler — health-check нод, уведомления, истечение подписок, сверка платежей, бэкапы |
| `postgres` | Основное хранилище |
| `redis` | FSM бота (состояния диалогов), троттлинг |
| `caddy` | Реверс-прокси с авто-HTTPS перед `api` |

`bot`, `api`, `worker` и одноразовый `migrate` — один и тот же образ
(`Dockerfile`), отличается только команда запуска. Это упрощает деплой
(один build) и позволяет независимо перезапускать/масштабировать каждую
часть при необходимости.

## Модель данных (ключевое)

- **User** — один на Telegram-аккаунт. `referral_code`/`referrer_id` — реферальная
  программа, `referral_balance` — бонусный баланс в рублях.
- **Server** (нода) — адрес, доступ к панели (пароль зашифрован Fernet),
  и закэшированные параметры Reality-инбаунда (публичный ключ, short-id,
  dest, server_names) — чтобы строить ссылки клиентам без обращения к
  панели на каждый показ.
- **Tariff** — тарифы хранятся в БД (не в коде), редактируются из бота.
- **Subscription** — у пользователя не больше одной; повторная оплата
  продлевает существующую запись, а не создаёт новую. Здесь же
  `xui_uuid` — единый VLESS-идентификатор клиента на всех нодах, и
  `subscription_token` — секрет для публичной ссылки.
- **SubscriptionServer** — на какой ноде у подписки реально создан клиент
  (`is_provisioned`) и текст последней ошибки, если создать не удалось —
  для повторных попыток воркером.
- **Payment** — `amount` (полная цена тарифа) и `applied_balance` (сколько
  списано бонусного баланса) хранятся раздельно: `amount - applied_balance`
  — это то, что реально ушло через эквайринг, и то, от чего считается
  реферальное вознаграждение (иначе баланс можно было бы «размножать»).

## Жизненный цикл подписки

```
buy:tariff / buy:trial
        │
        ▼
apply_paid_period() / create_trial()   (app/services/subscriptions.py — только БД)
        │
        ▼
sync_subscription_everywhere() / provision_on_all_active_servers()
        │            (app/services/provisioning.py — talks to XUI)
        ▼
add_client()/update_client() на каждой активной ноде (app/xui/client.py)
```

При добавлении новой ноды (`adm:nodeadd`) выполняется обратный проход:
`provision_new_node_for_existing_subscriptions()` создаёт клиента на новой
ноде для всех, у кого сейчас есть активный/пробный доступ — так подписка
"легко расширяется" без ручной работы с каждым пользователем.

При истечении (воркер, `expire_subscriptions`) — `revoke_subscription_everywhere()`
не удаляет клиента, а выключает (`enable=false`) на всех нодах, где он был:
это и снимает доступ, и позволяет мгновенно восстановить его при оплате без
пересоздания (то же UUID, тот же subscription-токен — ничего не нужно
перенастраивать в приложении пользователя).

Нездоровые (`is_healthy=false`) или отключённые админом (`is_active=false`)
ноды не трогаются на уровне XUI при обычной проверке здоровья — они просто
перестают попадать в `build_subscription_content()`, пока не восстановятся.

## Идемпотentность платежей

`app/services/payments.py::check_and_process_payment()` перечитывает платёж
через `SELECT ... FOR UPDATE` перед проверкой статуса — конкурентные вызовы
(вебхук + кнопка «Проверить оплату» + фоновая сверка одновременно) не могут
дважды продлить подписку по одному и тому же платежу. Источник истины по
статусу — всегда прямой авторизованный запрос к API провайдера, а не тело
вебхука.
